# Architecture

SupportOS is a **modular monolith**: one Node.js process, one SQLite database, background workers, and a built frontend served by the same process. No microservices, no cloud dependencies.

## Layers

```
src/
  shared/        domain types, zod schemas, constants, pure utilities
  server/
    config/      env config, structured logger (secret-scrubbing)
    database/    connection (WAL/FK/busy-timeout), migration system,
                 repositories (the ONLY layer that writes SQL)
    integrations/
      helpscout/ provider interface + real provider (OAuth + rate-limited
                 priority API queue, v3 reads / v2 writes) + fake provider
      lmstudio/  OpenAI-compatible local client
      qdrant/    vector store adapter (graceful fallback to FTS)
    sync/        SyncCoordinator: state machine, initial/incremental sync,
                 single-conversation sync, reconciliation
    ai/          prompts (versioned), provider interface, evidence builder,
                 tool registry (read-only), multi-stage pipeline
    search/      FTS5 search engine
    knowledge/   ingestion (MD/TXT/CSV/JSON/HTML/PDF/DOCX)
    analytics/   deterministic SQL metrics + report logic
    automation/  local rules engine with safety tiers
    security/    HTML sanitizer, redaction layer
    services/    app context (wiring), operations (write protection),
                 workers (job queues), webhook endpoint, backup service
    routes/      Fastify route modules + capability matrix
  client/        React app (pages, components, stores, typed API client)
```

## Key design decisions

### 1. The provider boundary (`HelpScoutProvider`)
The whole application depends on an interface, never on endpoints or API versions. `RealHelpScoutProvider` composes 14 service classes (users, teams, inboxes, fields, tags, saved replies, workflows, webhooks, customers, organizations, conversations, threads, reports, attachments) and hides the v2/v3 split: reads use the current v3 conversation endpoints, writes use the documented v2 operations. The UI never knows which version serves an operation. `FakeHelpScoutProvider` implements the same interface with an in-memory mutable world — powering demo mode AND the entire test suite (pagination, rate limits, merges, duplicate events, write flows) without touching a real account.

### 2. Sync engine
Polling + incremental sync is the primary mechanism (webhooks are optional — a localhost app cannot receive external webhooks without a relay). Every resource has a **checkpoint** (last success, cursor, processed/failed counts, last error, retries, status). The initial sync runs in dependency order (account → users → teams → inboxes → fields → tags → organizations → customers → conversations+threads → ratings → statuses) and is fully resumable — restarts never corrupt state and recovery never requires deleting the database. Incremental sync uses `modifiedSince` with a 10-minute overlap window and deduplicates by remote IDs. Remote/created/updated/local timestamps are never conflated.

### 3. Write protection
Every remote mutation follows: validate → verify auth → **read latest remote state** → compute desired state → perform → confirm → persist locally → audit. Tag updates are the canonical example: Help Scout's API is replacement-style, so SupportOS always fetches current remote tags and merges (`remote A,B + add C → A,B,C`, never `A,C` — covered by dedicated tests). Custom fields preserve system fields (Topics/Sentiment) when omitted, per documented behavior. Replies are idempotency-keyed and **never blindly retried** — after a timeout the UI says delivery is uncertain and asks the human to verify.

### 4. Provenance model
The database distinguishes remote source data (`raw_json` + hash retained for every entity, enabling schema-evolution tolerance), local derived data (support cases, metrics), AI-generated data (analyses, drafts, memories — always marked), and human local data (known issues, memories entered by people). Original data is never overwritten with derived data. Every AI source carries `{source_type, source_id, visibility}` and the UI renders sources as clickable evidence chips.

### 5. Job queues
SQLite-backed queues with priorities P0 (user send) → P4 (background indexing), atomic claim, bounded retries with exponential backoff, restart recovery (stale `running` jobs return to the queue). The rate limiter tracks Help Scout's documented headers (`X-RateLimit-Limit-Minute` / `Remaining-Minute` / `Retry-After`), counts writes double, and backs off automatically on 429.

### 6. AI pipeline
Separate stages (analysis → evidence retrieval → draft → verification → note → memory), each an `ai_runs` row with model, prompt version, input hash (caching), latency and output. Prompts live in one versioned module. Retrieval is deterministic (SQL + FTS + hybrid similar-conversation scoring that combines keyword, semantic (when available), same-customer, shared-tag and recency signals); the LLM explains, never counts. Customer-facing generation is bounded: customer-safe evidence only, anti-fabrication rules, redaction layer, then a strict verification pass whose findings (unsupported claims, missing questions, internal leakage) are stored and shown.

### 8. Startup sequence
validate environment → run migrations → initialize services → probe Help Scout/LM Studio/Qdrant (optional failures never block startup) → recover stale jobs → start workers → serve UI. In demo mode with an empty database, the initial demo sync + intelligence seeding run automatically.

### 9. Conversation activity engine (v1.7.0)
Help Scout exposes no historical change log — that API limitation shapes the whole design. The `conversation_events` table is a **derived, honestly-sourced** event history, not a claim of what happened upstream:

- **Message events** (`customer_message`, `human_agent_message`, `system_agent_message`, `internal_note`) are derived from the thread mirror with EXACT timestamps (`source: sync`, dedup key `thread:<remoteId>` — one event per remote thread, idempotent across re-syncs).
- **Change events** (`status_changed`, `assignment_changed`, `tag_added`…) observed during sync record the **observation time** with `observed: true` metadata — the change happened between two observations, and the event says so.
- **Local writes** (through `ConversationOperations` — status, assign, tags, fields, snooze, moves, priority, state) record their own exact time with `source: local`.
- **Rebuild events** (`source: rebuild`) derive once at migration/upgrade time from threads, conversation rows, attachments and Help Scout lineitem action records (conservative keyword mapping, raw action text preserved).
- `activity_history_complete = 0` flags conversations whose full thread history is not locally known; their response state is `unknown`, never "never responded".

**Derived activity columns** (first_response_at, customer_waiting_since, last_tag_change_at, … 14 total) are indexed on `conversations` and recomputed transactionally on every upsert — the same SQL the migration backfill uses, so fresh and upgraded databases converge. The **response-state machine** is a single SQL CASE (`RESPONSE_STATE_SQL`) shared by the list filter, the view engine and the detail route, with a JS mirror locked to it by a row-by-row equivalence test. **Saved Inbox Views** persist as Zod-validated JSON condition trees; the ViewEngine compiles them to parameterized SQL with whitelisted identifiers at evaluation time (calendar date modes re-resolve on every open). **Priority and custom ticket states** are local layers — `supportos_priority` never touches Help Scout data unless an explicit custom-field mapping is configured, and `ticket_state_transitions` records every transition (previous/new, actor, reason, timestamp) feeding per-state lifecycle metrics and bottleneck ranking.

### 10. Collaboration layer (v1.8.0)
Five systems built on one discipline: **derive team features from observable facts, never guess, and keep internal data on internal paths**.

- **Operations Center**: 16 tiles computed live, mailbox-scoped. Every conversation-scoped tile is a COUNT(*) over ONE whitelisted parameterized fragment (`tileFragments.ts`) — the *same* fragment `GET /api/conversations?ops=<tileKey>` uses for its drill-down list, so a tile and its list can never disagree (locked by parity tests + a live audit check). SLA tiles call `SlaService` directly (one business-minutes implementation in the codebase); system tiles (approvals, failed jobs, sync, campaigns) read the existing job/sync/outreach stores. Live updates ride the existing SSE bus.
- **Workload & capacity**: per-agent/per-team aggregates with **tiered weighted pressure** (each conversation counts once at its highest tier: urgent > SLA > waiting > open). Capacity is explicit configuration in `application_settings` (default max, per-user overrides, weights — never inferred); availability is the Help Scout `user_statuses` the mirror already syncs; the 7-day average active load is labeled an approximation (current-assignee attribution). The **suggested assignee** ranks available agents by resulting pressure and exposes its reasoning — read-only by construction.
- **Notification Center**: `NotificationSweep` is the **single producer** — one idempotent pass deriving every notification from observable facts (new `conversation_events`, SLA alerts, approval/failed jobs, sync state, campaign replies, known issues, spikes, `ai_runs`, ratings). Dedup keys make re-runs structurally duplicate-free; event-derived notifications reuse the event's own dedup key; state-derived ones include the day. The cursor **defers initialization until the first sync settles** (history is not news). Preferences gate at insert (disabled types produce no rows). Targeting: assignee/mention rows + broadcasts; list/read queries filter to the acting user (`me_remote_id`, first-user fallback). Runs in the worker loop (default 15s) + manual trigger; emits `notification-received` over SSE.
- **Mentions**: exact case-insensitive matching against the identity mirror (mention names, deterministic name fallbacks, team names with spaces) — never prefix/substring; unknown tokens stay plain text and create nothing. Mentions in internal notes are detected by the sweep; mentions in side-thread messages resolve at write time with immediate fan-out (team mentions notify every member except the author; self-mentions notify nobody). The "mentions for me" queue merges both sources, each row linking back to its conversation.
- **Side collaboration threads**: `side_threads` / `side_thread_participants` / `side_thread_messages` / `side_thread_mentions` (migration 012) are **internal-only by construction** — local tables, no provider path, never synced, never customer-visible; the UI states this. Participants are explicit rows (mentioning auto-joins), resolved threads reject messages (409), and every mutation writes `audit_log` entries. Routes validate user/team EXISTENCE before insert (unknown ids are 422, never FK 500s).

### 11. Intelligence layer (v1.9.0)
Three systems sharing one rule: **the AI is never the authority — it reads, explains and recommends; deterministic code decides, stores and writes.**

- **Local Copilot**: an interactive read-only assistant per conversation (`CopilotService`). The model can only act through the allowlisted tool registry (`AiToolRegistry` — 19 read-only tools: the six search tools plus conversation context, customer history, similar conversations, issue clusters, AI analyses, SupportOS metadata, the attribute snapshot, and the v2.0.0 workspace tools — incident search, custom object search, customer timeline and the gated connector data search — plus the v2.1.0 quality tools — knowledge gap and friction reports); **it never sees SQL**, every result is server-validated, bounded (chars, rows, limits) and redacted before it reaches the prompt, and the tool loop is hard-capped (max rounds + max tool calls; a looping model is stopped and must answer from what it has). **Citations are machine-generated**: the source list is derived from the tool executions the server actually performed — the model's claims about sources are never trusted, so a fabricated citation is structurally unrepresentable. Sessions and messages persist (`copilot_sessions` / `copilot_messages`, migration 013); every turn is audited (`ai_involvement=true`) and recorded in `ai_runs` with model, prompt version and latency. The Copilot has **no write path anywhere** — read-only by construction, not by policy. If AI is disabled or LM Studio is unreachable: honest 503s and visible error states, never fake answers.
- **AI attribute layer**: a closed 14-key catalog (`AI_ATTRIBUTE_CATALOG`) backed by `ai_attributes` (migration 013). Two computation layers: **deterministic** (zero AI — urgency, frustration cues, technical familiarity, escalation signal, question count, risk composite, known-issue and issue-cluster membership, customer goal, response style: from stored interaction cards and local facts) and **AI** (LM Studio, cached by input hash + prompt version — intent, product, feature, issue, customer goal, response style: stored only with enum-closed values, and medium/high confidence requires an evidence excerpt whose thread reference was actually in the prompt). `saveSnapshot` re-validates every record against the catalog (unknown keys, enum/boolean/number violations and type disagreements are dropped, never stored) and **versions every row** (recompute stamps `superseded_at`; full history survives) — a key with no current row IS the honest `unknown`. Attributes are local intelligence only: own table, own schema version, never written to Help Scout. Consumption: the **live inbox filter** (`aiAttribute`/`aiAttrOp`/`aiAttrValue` on `GET /api/conversations`), **saved Inbox Views** (`ai_attribute` condition kind), **Outreach segments** (`aiAttribute` ticket condition) and **automation rules** — the inbox filter compiles through the *same* `viewEngine` path as saved views (one implementation; a live filter and a saved view can never disagree about what `urgency: high` means), and the AI Center exposes a coverage report (known vs unknown per attribute) plus searchable conversation drill-downs.
- **AI escalation rules**: `automation_rules` conditions grow two fields — `ai_attribute` (requires a catalog key) and `ai_verification` (`failed`/`passed`/`none` from the latest draft verification) — Zod-validated at the API boundary. Matching semantics follow the attribute's value type (numeric comparisons for `question_count`, vocabulary-position comparisons for ordered enums); **a missing attribute reads as `unknown`: it matches `equals unknown` and never a concrete value**. The safety invariant is unchanged: conditions only decide whether a rule MATCHES — actions flow through the existing read / non-destructive / higher-risk approval tiers, so the AI can route a ticket to the review queue but can never write to a customer.

### 12. Intelligence workspace layer (v2.0.0)
Eight systems (plan phases 18-25) built on the same honesty rules as everything above: derived over stored, closed vocabularies, idempotent by construction, association wording for every correlation, and explicit human control over anything AI-visible or customer-facing.

- **Incident workspace**: `incidents` + `incident_conversations` / `incident_related` / `incident_refs` / `incident_releases` / `incident_notes` / `incident_events` (migration 014) are LOCAL-ONLY (no Help Scout write path exists). Codes are `INC-###` generated inside the insert transaction; every mutation appends a dedup-keyed timeline event (`INSERT OR IGNORE` — re-runs cannot double-record); status transitions maintain `resolved_at` consistency. **Affected customers/organizations are derived from the linked conversations at read time** — never stored, so they cannot drift. `IncidentService` wraps mutations with `incident_update` notifications through the single-funnel sweep. Declare-from-known-issue / declare-from-cluster endpoints pre-fill the workspace and bulk-link member conversations.
- **Issue impact intelligence**: ONE `IssueImpactService` serves incidents AND known issues (only the link table differs). Counts are `COUNT(DISTINCT customer)` — never ticket counts; growth is last-7d vs previous-7d with an explicit direction; products come from the current AI attribute layer and read honestly `unknown` until analyzed; release correlation counts conversations starting within 7 days after a recorded release date and the non-causal wording lives in the returned data itself.
- **Extended Issue Radar**: six new deterministic detections (reappearing, customer concentration, inbox concentration, release-correlation bursts, repeated-unresolved, global volume spike) computed in one batched pass with julian-day arithmetic; every alert carries evidence conversation links; the audit greps radar details for causal wording.
- **Custom objects**: types define typed fields (`custom_object_types` / `custom_object_fields`); values are JSON in `custom_objects`, validated at every write by a Zod schema built from those definitions (strict — unknown keys rejected; enum-closed selects; field types immutable once objects exist). Relationships are edges in `custom_object_links` (closed target vocabulary, existence-checked → 422 never FK 500). Full-text search via `fts_custom_objects` (quoted-prefix pattern). **User-defined data never becomes SQL.**
- **Connectors**: `ConnectorService` refreshes four source kinds into `connector_rows` with snapshot semantics — rows keyed by a configured key column or a stable content hash; vanished rows pruned by key-set diff (deterministic even sub-second); failures set `health=error` and never partially overwrite a good snapshot. Files resolve inside the `connectors/` folder jail (containment re-checked beyond the schema). HTTP targets pass the fail-closed `ssrfGuard` (protocol allowlist; loopback/RFC1918/CGNAT/link-local metadata/IPv6 private/loopback/link-local; IPv4-mapped and numeric encodings; `.local`/`.internal` hostnames) — validated at create/patch AND re-validated with DNS resolution before every request (rebinding shapes refused). Auth material is stored locally and redacted (`••••••`) in every read path. **The `allowed_ai` flag gates the Copilot's `search_connector_data` tool** — non-allowed connectors get an explicit refusal naming what IS visible.
- **Customer event timeline**: `customer_events` is an append-only, dedup-keyed log per customer with a closed 12-kind union. `CustomerEventSweep` derives observable events (signup, conversation created/closed, first customer message, campaign sent/replied, rating, incident exposure, custom object links) every 60s — silent while the first sync populates — plus a full idempotent `rebuild()`. Kinds with no observable source (subscription/account/product/integration) stay **absent until a connector or custom object produces them**. Organization timelines are the union over member customers (no copies).
- **Support health**: `SupportHealthService` computes operational metrics per customer/organization from one parameterized subject id (member subselect for orgs): every metric carries a definition, completeness label and bounded evidence conversation ids; attention flags link to the evidence. **No aggregate score exists** — the schema has no such field and the audit asserts its absence.
- **Knowledge freshness**: `last_reviewed_at` / `last_verified_at` (PRAGMA-guarded ALTERs) + `knowledge_doc_usage` counters (bumped per search, deduped per document). The report computes six deterministic flags (stale by threshold setting, review gap, title-overlap conflict candidates, low usage, followed-by-tickets via FTS topic match within 14 days after the last update, recurring-question association) — **review/verify are human-only mutations; nothing edits or publishes automatically**.

### 13. Quality layer (v2.1.0)
Seven systems (plan phases 26-33) that turn the intelligence inward — SupportOS reviews its own work, under the same rules: deterministic detection, evidence-first, human decisions, association wording, closed vocabularies.

- **Knowledge gap engine**: `KnowledgeGapService` + `knowledge_candidates` (migration 015) with a closed five-kind union and stable `kind + normalized question` dedup keys. Rebuilds upsert evidence (occurrence counts, conversation ids, method notes) and **never overwrite a human decision** — `decide()` only mutates rows still in `candidate` status (409 otherwise). The `draft()` endpoint returns a suggested title/outline with evidence conversations; **no code path writes to `knowledge_documents`** — approval is a marker, authorship is human.
- **Post-resolution QA**: `PostResolutionQaService` + `post_resolution_qa` (one row per conversation). The deterministic tier computes from the mirrored threads (back-and-forth excluding closing acknowledgments, repeated 6-word spans with thread evidence, messages after close, handoff counts with the pre-sync-unknown caveat, first-response/resolution minutes with a first-reply-thread fallback). The AI tier runs through an injectable `QaChatFn` (the Copilot pattern), recorded as `ai_runs` type `post_resolution_qa` — **a separate type from draft verification by design** — with closed-value coercion (anything unrecognized becomes `unclear`), unparseable output failing honestly, and suggestions that are recommendations only. AI failure → honest 503 stating the deterministic tier was still computed and stored.
- **Response effectiveness**: `ResponseEffectivenessService` joins `client_support_outcomes` to conversations (window-bounded), classifies reply text for two independent characteristics (documentation link, technical explanation — reported as non-exclusive, never as styles), aggregates follow-up/clarification/resolution/effort/ratings per bucket with sample conversations. **The honesty notes live in the data** ("OBSERVED ASSOCIATIONS… do not show causation"), and the black-box audit greps effectiveness + builder notes for causal vocabulary.
- **Friction analyzer**: `FrictionAnalyzer` + `friction_findings` (UNIQUE conversation × kind, upsert with stale-kind pruning). Six deterministic detections, each pinned to thread ids + excerpts: repeated spans (≥ 6 normalized words across separate customer messages), repeated normalized agent questions, troubleshooting-loop restatements after agent replies, handoffs from `conversation_events`, customer-level 90-day same-tag recurrence, duplicated information requests (request-category + entity-shape, or direct complaint phrases). Every detail line self-describes as a heuristic — **patterns, never judgments about people**.
- **Translation**: `detectLanguage` is deterministic and exported — script ranges first (Hangul before Han; Han → Chinese with low confidence and an explanatory note), function-word frequency for Latin scripts (URLs/emails/code stripped first), `unknown` as an honest terminal state. `TranslationService` translates through an injectable chat fn ONLY (LM Studio; **no cloud fallback exists anywhere**), caches by sha256(source|target|purpose|text) so identical requests never re-run the model, preserves technical terms/code/URLs/emails via the system prompt, and refuses same-language and undetectable-source requests honestly. Side-by-side rendering in the conversation detail; sending stays on the normal human write path.
- **Advanced segmentation**: seven new condition kinds + ticket `customFields`/`channel` in the shared contract, evaluated set-per-node in `SegmentEngine` with whitelisted identifiers and bound values; unknown kinds/ids match NOTHING (safe deny — regression-locked after the audit found `history_issue` falling through to a default link table). The **NL suggestion** (`SegmentSuggestService`) prompts the local model with the closed-kind catalog, validates the proposal with a strict structural validator (depth/node budgets, per-kind field checks, AI-attribute catalog membership), then **the deterministic engine executes the selection** — the route returns the engine's preview, nothing is saved, and hostile proposals fail as clean 422s.
- **Report builder**: `ReportBuilderService` compiles metric × dimension from code-side closed catalogs (20 metrics, 14 dimensions) — the config selects catalog keys and provides typed filter values, **never SQL text**; a final safety guard refuses compiled SQL that smells of DDL/DML. Rate metrics are SUM(CASE)/COUNT expressions; `ai_attribute_share` binds its SELECT-position parameters before WHERE parameters (positional binding, regression-locked); comparisons re-run the identical query over the previous window. Saved definitions persist in `report_definitions`. Every run response embeds the metric's definition and limitations (plan requirement), and the origin is labeled `local` — native Help Scout reports stay under their own tab with their own origin labels.
- **Copilot tools +2** (19 total): `get_knowledge_gaps` and `get_friction_report` — read-only, bounded, redacted, carrying their own honesty notes.

## Database

~85 tables across fifteen migrations (see `src/server/database/migrations/`; migration 011 adds `conversation_events`, `ticket_states`, `ticket_state_transitions`, `inbox_views` and the derived activity columns on `conversations`; migration 012 adds the collaboration tables — `notifications`, `notification_prefs`, `side_threads`, `side_thread_participants`, `side_thread_messages`, `side_thread_mentions`; migration 013 adds the intelligence tables — `ai_attributes` (versioned attribute snapshots with `superseded_at`) and `copilot_sessions` / `copilot_messages`; migration 014 adds the workspace tables — `incidents` + link/event/ref/release/note tables, `custom_object_types` / `custom_object_fields` / `custom_objects` / `custom_object_links` + `fts_custom_objects`, `connectors` / `connector_rows`, `customer_events` (with an idempotent observable-history backfill) and `knowledge_doc_usage` + the freshness columns on `knowledge_documents`; migration 015 adds the quality tables — `knowledge_candidates`, `post_resolution_qa`, `friction_findings`, `translation_cache` and `report_definitions`, all computed on demand with no backfill). FTS5 virtual tables are maintained by repositories (delete+insert pattern) and can be rebuilt from base tables at any time (Sync Health → Rebuild search index); the activity engine has its own idempotent global rebuild (`POST /api/conversations/activity/rebuild`); the attribute layer recomputes per conversation on demand or via the `compute_attributes` worker job (bounded v1.9.0 backfill covers previously analyzed tickets). WAL mode, foreign keys, busy timeout 5000ms, prepared statements everywhere, batched writes in transactions.

## Frontend

React 19 + Vite. Server state via TanStack Query (never the whole database in the browser); UI state via Zustand; composer state is component-local so AI actions and network failures **never lose typed text**. The design system is hand-rolled CSS (dense, professional, desktop-first, dark/light themes) — no marketing chrome. Accessibility: semantic controls, ARIA labels, visible focus, keyboard shortcuts (⌘K command palette, `/` search, `g`+`d/i/s` navigation).
